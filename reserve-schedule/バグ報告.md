# 深刻度: 致命的

## [致命的] 同時に予約が入ると、両方のお客様に「予約完了」が表示されたうえで片方の予約が消滅する 【再現済み】

- **場所**: `shared.js:438-468`（`Ledger.api.createReservation`）。重複チェック `443-451` と保存 `462-463` の間、および `loadReservations()`（`198`）→`saveReservations()`（`204`）という read-modify-write 全体。
- **再現手順**:
  1. 同一ブラウザで予約ページを2つのタブで開く。
  2. 両タブでまったく同じ日時（例: 5日後 14:00〜15:30）に対して `createReservation` を**同時に**発火させる。
     実測は Playwright で `Promise.all([tabA.evaluate(create), tabB.evaluate(create)])` として10回試行。
  3. 各回、両タブの戻り値 `ok` と、`localStorage` に最終的に残った予約件数を確認。
- **何が起きるか**: **10回中9回**、両タブとも `ok:true`（＝両方のお客様の画面に「ご予約ありがとうございます」の完了画面が出る）となった。しかもその9回すべてで、`localStorage` に残った予約は**1件だけ**だった。つまり、
  - 一方のお客様は完了画面を見たのに、予約がどこにも存在しない（無断キャンセル扱いになる）。
  - もし保存が両方成功する経路（フェーズ②のサーバー化後の素朴な実装）になれば、今度は本物のダブルブッキングになる。
  - なお**逐次**（タブ2が確定 → その後タブ1が確定）の場合は正しく拒否された。壊れるのは並行時のみ。
- **あるべき挙動**: 重複チェックと保存が不可分（アトミック）に行われ、後から来た側は必ず「この時間帯はすでに予約されています」で拒否される。予約が消えることは絶対にあってはならない。
- **修正案**:
  - **フェーズ②（本命）**: D1 側で `reservations(date_iso, start_min)` に一意制約を張るか、`INSERT ... SELECT ... WHERE NOT EXISTS (重なる行)` を1本のSQLで実行し、影響行数0なら競合として拒否する。「SELECT で確認してから INSERT」という2文構成にしないこと。
  - **フェーズ①の暫定策**: `createReservation` の中で `loadReservations()` → 重複チェック → `saveReservations()` を実行したあと、**保存直後にもう一度読み直して自分のIDが残っているか・重なる他予約が混入していないかを検証**し、崩れていればロールバックしてエラーを返す。または `navigator.locks.request()` で同一オリジン内の排他を取る。
  - ※「localStorage であること」自体は既知の前提だが、**この競合はフェーズ②の設計にそのまま持ち込むと本物のダブルブッキングになる**ため、致命的として報告する。

- **対応状況**: フェーズ①では暫定緩和で対応（コミット: `data-layer` 系コミット、詳細はgit logを参照）。`shared.js` の `createReservation` に、①`navigator.locks`が使える環境ではロックで直列化、②保存直後に読み直して自分のIDが残っているか・重なる他予約が混入していないかを検証、③壊れていればこの呼び出し分の予約だけを取り除いてエラーを返す、という3段構えの緩和を実装した。**「完全に防げた」わけではない**旨をコードコメントに明記済み。実機確認: バグ報告と同じ手法（同一Playwrightコンテキストで2タブを開き `Promise.all` で同時に `createReservation` を発火）を10回試行し、**10回とも「両方ok:trueになる」「完了画面が出たのに予約が消える」のいずれも再現しなかった**（1件が拒否され、保存されている件数とok:trueの件数が常に一致することを確認）。完全な解決はフェーズ②でD1のユニーク制約または単一INSERT文（`WHERE NOT EXISTS`）によって行う方針とし、README「D1テーブル設計案」冒頭に⚠付きで目立つように明記した（「SELECTで確認してからINSERT」という2文構成にしないことも明記）。

## [重大] 画面を開いたまま時間が経つと、受付締切（2時間前）を過ぎた枠・過去の日時をそのまま予約できてしまう 【再現済み】

- **場所**: `shared.js:438-468`（`createReservation` が `computeAvailableStartTimes` / `isBookableDate` / `CUTOFF_MIN` を一切再検証していない）。空き判定は `shared.js:369-413` にあるが、確定時には呼ばれない。
- **再現手順（受付締切）**:
  1. 時計を 2026-08-13 13:00 に固定して予約ページを開く。
  2. 60分メニューを選び、STEP2 で「本日」を選択。空き枠は `15:30, 16:00, …`（＝2時間後以降）と正しく表示される。
  3. 15:30 を選び、STEP3 でお客様情報を入力して STEP4 まで進む。
  4. **STEP4 に留まったまま時計を 14:30 に進める**（15:30 開始は残り1時間＝締切超過）。
  5. 規約に同意して「予約を確定する」を押す。
- **何が起きるか**: **そのまま確定し、完了画面が表示される。** 保存された予約は `2026-08-13 / startMin=930（15:30）`、確定操作の時点で現在時刻は 14:30。締切2時間前ルールを破った予約がサロン側に入る。
- **再現手順（日付変更を跨ぐ）**:
  1. 時計を 2026-08-13 20:00 に固定してページを開く。本日の残り枠 `22:30, 23:00` が表示される。
  2. 22:30 を選んで STEP4 まで進む。
  3. **時計を6時間進める（＝8/14 02:00）**。
  4. 「予約を確定する」を押す。
- **何が起きるか**: **確定できてしまう。** 保存されるのは `2026-08-13 22:30`、つまり**すでに過ぎ去った日時の予約**。管理画面の予約一覧にも「過去の予約」として残り続ける。
- **あるべき挙動**: 確定処理の中で、確定時点の現在時刻を使って「予約可能範囲内か」「受付締切を過ぎていないか」を再判定し、外れていれば「申し訳ございません。受付を締め切りました。別の時間をお選びください」と表示して STEP2 に戻す。
- **修正案**: `createReservation` の冒頭で、重複チェックと同じ場所に以下を追加する。
  ```js
  var cfg = getEffectiveConfig();
  var ok = computeAvailableStartTimes({
    dateISO: payload.dateISO, totalMinutes: payload.totalMinutes, now: new Date(),
    reservations: loadReservations().filter(r=>r.dateISO===payload.dateISO),
    blockedSlots: loadBlockedSlots().filter(b=>b.dateISO===payload.dateISO),
    serviceWindow: /* menuIds から再計算 */, cfg: cfg
  }).indexOf(payload.startMin) !== -1;
  if (!ok) return { ok:false, error:"..." };
  ```
  既存の純粋関数をそのまま使えるので追加ロジックは不要。**この1箇所を直せば、次の項目の大半も同時に塞がる。**

- **対応状況**: 修正済み。修正案どおりではなく、次項の payload 検証と統合した `validateReservationPayload(payload, ctx)`（`shared.js`、`Ledger.api` の外の純粋関数）の中で、`computeAvailableStartTimes` を確定時点の `now` で呼び出して判定するようにした（切り出した専用チェックにはせず、他の検証と1回のパスにまとめた点が修正案との違い）。判定結果がNGなら `code:"UNAVAILABLE"` を返し、`index.html` 側はこれを受けてSTEP2へ戻し、日本語で「申し訳ございません。ただいま受付を締め切りました。恐れ入りますが別の日時をお選びください。」と案内した上でその日の枠を再描画する。実機確認: バグ報告の再現手順（Playwright Clock APIで13:00固定→15:30予約→14:30に進めて確定、および20:00固定→22:30予約→翌日02:00に進めて確定）をそのまま実行し、**いずれもSTEP5（完了画面）に進まず、STEP2に戻り、localStorageに不正な予約が保存されないこと**を確認した。

## [重大] localStorage の JSON が壊れると、全予約が黙って消え、次の保存で完全に上書きされる 【再現済み】

- **場所**: `shared.js:198-203`（`loadReservations` の `catch(e){ return []; }`）。`loadBlockedSlots`（`210-215`）・`loadSettings`（`169-174`）も同じ構造。
- **再現手順**:
  1. 予約を数件作成する。
  2. `localStorage.setItem("cocosiaBooking.reservations", "{壊れたJSON")` で保存値を破損させる（拡張機能の干渉、容量超過による書き込み途中終了、別タブとの競合などで起こりうる）。
  3. `Ledger.api.getReservations({})` を呼ぶ → **件数0**。エラーも警告も出ない。
  4. その状態で新しい予約を1件作成する。
  5. 再度 `getReservations({})` を呼ぶ → **件数1**（新しい予約のみ）。
- **何が起きるか**: 管理画面には「確定した予約はまだありません。」と表示される。オーナーは全予約が消えたことに気づかないまま営業し、次に1件でも予約が入った瞬間に**壊れた元データが正常なJSONで上書きされ、復旧手段が完全に失われる**。
- **あるべき挙動**: パース失敗は「データが空」ではなく「読み取り不能」として区別し、上書き保存を止めたうえで画面に明示的なエラーを出す。
- **修正案**: `loadReservations` を `{ ok:true, list }` / `{ ok:false, raw }` を返す形にし、`ok:false` のときは `saveReservations` を実行させない。最低限の暫定策として、`catch` の中で破損した生データを `cocosiaBooking.reservations.corrupt.<timestamp>` に退避したうえで `console.error` を出し、画面にも警告を表示する。

- **対応状況**: 修正済み（修正案とほぼ同じ形。外部エクスポートはしていない点のみ異なる）。`loadReservations`/`loadBlockedSlots`/`loadSettings`（いずれもshared.js内部専用で外部に公開していないため、外部契約を変えずに内部形式だけ変更できた）が `{ list, corrupted }` を返すよう統一し、破損検知時は①壊れた生データを `<key>.corrupt.<timestamp>` に退避、②`<key>.corruptFlag` を立てる、③`console.error`で記録、を行う。`saveReservations`/`saveBlockedSlots`/`saveSettings` はフラグが立っている間、書き込みを拒否する（＝壊れたデータが正常なJSONで黙って上書きされない）。`createReservation`/`cancelReservation`/`updateReservationContact`/`createBlockedSlot`/`deleteBlockedSlot`/`updateSettings` は破損検知時に明示的なエラーメッセージを返す。画面側の警告表示は `Ledger.api.getStorageHealth()` を新設し、`admin.html` に破損時のみ表示される警告バナー（「破損データを消去して再開する」ボタン付き、`acknowledgeStorageCorruption`で解除）を追加、`index.html`も起動時にチェックしトーストで警告する。実機確認: Node上のユニットテストで、`localStorage.setItem("cocosiaBooking.reservations","{壊れたJSON")`のあと`getReservations({})`が空配列を返す（例外を投げない）こと、破損フラグが立つこと、退避キーにデータが1件保存されること、**破損中は新規予約の保存が拒否され元の壊れたデータが上書きされないこと**、`acknowledgeStorageCorruption`で解除後は正常に保存できることを確認した。ブラウザでの警告バナー表示は目視確認はしていない（Node上のAPIレベル確認のみ）。

- **場所**: `index.html:754`（`var CFG = L.BOOKING_CONFIG;`）と、それを使う `index.html:944`（`L.bookableRange(now, CFG)`）・`index.html:966`（`L.isBookableDate(dISO, now, CFG)`）。

- **再現手順（範囲を狭めた場合）**:

  2. 予約ページを開き、メニューを選んで STEP2 へ。
  3. カレンダーを見る。

  1. 「予約可能日数」を **120** にして保存。
  2. 予約ページ STEP2 でカレンダーの「›」を押し続ける。

- **参考**: 営業時間の設定（12:00→10:00〜18:00）は `getAvailability` 経由なので**正しく反映された**（枠が `10:00..17:00` の15件になることを確認）。ずれているのは日付範囲の判定だけ。
